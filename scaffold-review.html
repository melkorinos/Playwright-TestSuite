Playwright-TestSuite — Scaffold Review

A fork-and-adapt skeleton for API + E2E testing. Reviewed only where it matters for an agnostic, ready-to-implement scaffold: how it's wired, and whether the docs tell the truth.

in scope · architecture & wiring in scope · docs accuracy auth behaviour multi-user interaction

Placeholder domains (auth, services, interaction) are intentional — judged as scaffolding, not as a finished system.

Bottom line. The skeleton is wired well — lazy fixtures, clean service factories, worker isolation. Two things undercut its fork-and-go purpose: a couple of wiring inconsistencies a newcomer inherits silently, and a README that describes a repo that no longer exists. Both are cheap to fix and high-leverage for a scaffold.

1 · Architecture & wiring

Tests import one test object; fixtures/fixtures.ts lazily merges the browser and service fixture groups, so API tests never spawn a browser. That backbone is sound. The issues are at the edges: two browser agents that behave differently, dead fixture files, and a missing quality gate.

The asymmetry, up close

Both fixtures present the same BrowserAgent type and share the page-object factory assembleBrowserAgent(page), so a test treats them as interchangeable — but they aren't. browserAgent1 rides the built-in page and inherits the full project config; browserAgent2 builds its own context, and the code itself admits it doesn't propagate actionTimeout/navigationTimeout (browserAgents.ts:56-58). Same shape, different behaviour = a leaky abstraction someone debugs the hard way later.

A2

Agent fixtures behave differently (timeouts not propagated into agent2's newContext). Build the context with the project timeouts so the agents are truly interchangeable.

A4

fixtures/webPages.ts + webComponents.ts define standalone fixtures that are never merged (their shape is re-implemented inline in browserAgents.ts). Dead code → newcomer wires the wrong file. Delete or integrate.

D3

Configs exist (.prettierrc, eslint.config.mjs) but no lint/format/typecheck scripts, eslint/prettier aren't even in deps, and CI runs tests only. Wire the gate the toolchain implies.

2 · The front door describes a different house

For a "clone and go" scaffold the README is the product. This one misdescribes its own structure and mechanism — the single most damaging defect for the stated purpose, and the cheapest to fix.

says Repo structure

.github/components/ + .github/tests/

reality

They live in e2e/components/ + e2e/tests/.

says CI

"GitHub Actions / Azure DevOps pipeline templates"

reality

No ADO — only .github/workflows/ (GitHub Actions).

says AI agents

VS Code Copilot · .vscode/settings.json · .github/prompts/ · /pr-review · /test-healer

reality

.vscode/ and .github/prompts/ don't exist; those commands are gone. Interface is now Claude Code — .claude/commands/ + CLAUDE.md — never mentioned.

says browserAgent2 A3

"independent browser process via the playwright fixture"

reality

Uses browser + contextOptions; it's an isolated context, same process. Correct choice — just stop overstating it (also in the browserAgents.ts:50 comment).
