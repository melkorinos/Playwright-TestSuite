Playwright-TestSuite — Honest Architecture Review

A fork-and-adapt skeleton for API + E2E testing, judged against its own promise: clone it, point it at a new app, write tests fast — with multi-user interaction built in.

Scope: setup · architecture · wiring  |  Verified against source, not assumed.

Bottom line. Architecturally competent skeleton — but it undersells the one feature it's built around (multi-user interaction), ships auth code that fails silently, and its onboarding doc describes a project that no longer exists. For a "fork it and go" scaffold, the docs-vs-reality drift is the most damaging part.

1 · How the wiring actually fits together

Tests import a single test object. fixtures.ts lazily merges two fixture groups; Playwright only instantiates what a test references — so API tests never spawn a browser. That part is clean.

2 · The headline feature is the weakest link

The selling point is "two users interacting." Yet the dual-agent example just navigates both agents to the same URL independently — there is no agentA acts → agentB observes scenario. The differentiator has no real demonstration, and the two agents aren't even symmetric.

3 · The silent auth cascade

Auth originates in tokenService.getToken(), which returns response.json() with no status check. A failed token call yields garbage → every downstream request carries Bearer undefined → 401s with no traceable cause. Missing credentials are silently coerced to ''. Both violate the repo's own explicit-status convention.

4 · The front door describes a different house

For a "clone and go" scaffold the README is the product. This one misdescribes its own structure and mechanism — the single most damaging defect.
